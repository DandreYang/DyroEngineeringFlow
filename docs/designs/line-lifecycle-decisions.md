# 开发线生命周期与跨线合并：待定设计决定（推荐稿）

状态：维护者已于 2026-11-13 全部确认
日期：2026-11-13
依据：`line-lifecycle-and-cross-line-merge.review-v2.md` 第二轮审查结论"剩余维护者决定"①–⑥，以及其中 N1–N6 三个高风险问题和三个中风险问题。

总原则：首批只承诺能被代码验证、能从中断中说清状态的行为。宁可如实报告"只完成了一部分"，也不承诺做不到的原子性。这与 `delivery-physics.md` 的两条要求一致：区分"声称"与"可核验事实"，状态的寿命不超过它所依据的事实。

---

## ① 多仓操作承诺什么："全仓原子"还是"如实的部分完成"

**推荐**：不承诺跨仓原子。只承诺以下四点：

1. **逐仓按固定顺序执行**：按仓库 ID 排序。
2. **出错时在进程内尽力回滚**：沿用现有 `merge_line` 的回滚机制。
3. **写持久的操作日志**：`.dyro/ops/<op_id>.json`。每次 Git 变更之前先写下"意图"（仓库、原 HEAD、目标 SHA），完成后再写"结果"。
4. **发现未完成的操作就停下**：进程被杀后，再次运行同一命令或 `--recover`，会读日志并逐仓报告"已完成 / 未开始 / 状态不明"。第一批不自动跨进程回滚，只报告，并给出可以手动执行的恢复命令。

对外措辞一律改为"逐仓执行，失败时尽力回滚；中断后可查明每个仓的状态"。去掉"全仓原子"。

**取舍**：

- 完整的两阶段事务需要每个仓都能预提交，并有跨进程的协调者，复杂度远超首批的范围。
- 只做进程内回滚又无法应对进程被杀，第二轮审查的 N2 正是指这一点。
- 操作日志是让"中断后说得清"成立的最低成本。

## ② 顶层线合回基线：目标是谁，如何验证，用哪把锁

**推荐**：

- **目标**：锚点仓库 `repositories/<repo>` 当前检出的基线分支 `line.base_for(repo)`。同时满足以下条件才执行：
  - 锚点仓库的工作区干净；
  - 当前分支就是这个基线分支；
  - 没有进行中的 Git 操作（rebase、merge、cherry-pick 等）。
  
  不满足就拒绝，并说明原因。不自动切换分支。
- **锁**：每个物理仓库路径一把锁，即"物理资源锁"，键为锚点路径的规范化形式。
  - 所有会改动 Git 状态的入口都必须先拿这把锁：create、spawn、merge、sync、retire、task merge。
  - 多仓操作按仓库 ID 排序加锁，避免死锁。
  - 拿到锁之后，再做一次全部检查（干净、分支、HEAD），不复用锁外的检查结果。
- 这同时解决审查的 N1：retire 和 merge 用的锁不一致。

**取舍**：现有的"每条线一把锁"保留，作为外层锁。物理资源锁是新增的内层锁。改动面涉及所有写入口，所以要在首批里一次改完。

## ③ retire 的检查点、恢复与锁文件

**推荐**：

- 每个仓库的步骤固定为三步，每一步都写进 ① 的操作日志：
  1. 把当前 HEAD 保存为 `refs/dyro/retired/<line>/<repo>`；
  2. 移除工作区，不用 `--force`；
  3. 删除分支，前提见 ④。
- **全局顺序**：所有仓库都处理完之后，才把清单（manifest）移到 `.dyro/lines/retired/<line>.toml`，然后写退役事件，最后删除这条线的锁文件。
  - 这样任何一步中断，清单都还在原位，重新运行 `retire` 可以从日志继续往前做。
  - 这同时解决审查的 N2：事件写在分支删除之前、中途失败后无法判断进度。
- **恢复**：只向前继续，不撤销。已经移除的工作区不自动恢复，但第 1 步保存的 ref 使它总能手动恢复。
- 只有在清单已经归档、确认没有其他持有者之后，才删除锁文件。现有锁的实现（`state.py`）需要先核实，确认删除锁文件是安全的。

## ④ 共用分支和 anchor-reference 仓库能否在 retire 时删除分支

**推荐**：retire 只删除"确定只属于本线"的分支。以下任一情况都只解除关联，不删分支：

- 仓库的存储方式是 `anchor-reference`：只移除链接，从不删除锚点里的分支；
- 还有其他已登记的线引用同一个分支名；
- 锚点仓库当前检出的就是这个分支；
- 分支 HEAD 和第 ③ 步保存的 SHA 不一致，说明被别人推进过。

`--force` 不能越过这些限制。它只放宽一件事：分支没有被集成目标包含时，也允许删除。前提是第 ③ 步已经保存了 ref。

这解决审查的 N3：可能删掉别的线还在用的分支。

## ⑤ 退役后的线 ID、任务引用和家族频道历史

**推荐**：

- 归档的清单 `.dyro/lines/retired/<id>.toml` 同时就是"墓碑"。create 和 spawn 遇到同名墓碑一律拒绝，ID 永不复用。
- 还有未完成的任务（状态不是 done）引用这条线时，retire 拒绝执行。已完成的任务和 Objective 仍可以通过归档清单读到这条线的信息。
- 家族频道的历史消息只读保留：`line inbox --line <退役线>` 从归档清单解析所属家族。不再接受对退役线的 `line post`。
- 审查的 N5（子线损坏时父线也无法 retire）：先 retire 子线。子线的工作区已经缺失时，允许 `retire --missing-ok` 跳过移除工作区这一步，其余步骤照常执行。父线仍然要求先处理完直接子线，不放宽。

## ⑥ 部分仓库集成算不算成功

**推荐**：

- 源线所有仓库都在目标线里，并且全部合入，才报"已合入"。
- 源线有目标线没有的仓库时，结果标为 `partial`，并列出被排除的仓库。退出码非 0，可以用 `--allow-partial` 改为 0，但输出里仍标明 partial。
- 两边仓库没有交集时直接拒绝。
- 事件和台账记录实际合入的仓库列表，不写"整条线已合入"。

## 仍需补齐的命令定义（审查 N6）

v3 草稿需要写全以下三个参数的语法和状态转移：

- `--integration-ref`：retire 时用来做包含检查的目标，默认是父线分支，顶层线默认是基线。
- `--recover`：读取操作日志，向前继续。
- `--missing-ok`：见 ⑤。

审查 N4 也要一并处理：调用方的 FAIL 白名单要保留 `FAIL repository` 和观察超时这两类，继续按失败处理。
